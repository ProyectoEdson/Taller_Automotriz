# Despliegue en Vercel / Neon

Guía de la configuración usada para publicar la aplicación en Vercel con PostgreSQL en Neon. La app usa Next.js 15.5.29, Prisma Client/CLI **6.0.0** y PostgreSQL. Esta guía no autoriza publicar credenciales ni el seed demo.

## Configuración de Vercel y Neon

1. En Vercel, importar el repositorio y seleccionar **Root Directory `web/`**, preset Next.js y Node.js **22.x**. No copiar `web/.env` al repositorio. Verificar que el build desde `web/` genere Prisma Client antes de usarlo; el flujo local comprobado es `npm ci`, `npx prisma migrate deploy`, `npm run build`. [Vercel: Root Directory y build](https://vercel.com/docs/builds/configure-a-build#root-directory).
2. En el proyecto Neon, usar una base separada de desarrollo, con una URL **pooled** (`-pooler` en el hostname, TLS) para `DATABASE_URL` de las funciones y una URL **directa** únicamente para migraciones/administración. Guardar secretos en variables del entorno gestionado, no en Git. La base local sigue en Docker. Neon usa PgBouncer en **transaction mode**; no usar funciones de sesión como `SET`, `LISTEN` o tablas temporales por la URL pooled. [Neon: pooling](https://neon.com/docs/connect/connection-pooling), [Prisma: PgBouncer](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/pgbouncer).
3. Para migrar un entorno remoto **solo tras aprobación**, ejecutar `prisma migrate deploy` desde un proceso administrativo con `DATABASE_URL` configurada temporalmente a la URL **directa**, nunca desde las funciones pooled ni mediante `prisma migrate reset`. Después, la aplicación usaría su URL pooled. No ejecutar `prisma db seed` en producción: incluye usuarios demo con contraseñas conocidas. No ejecutar `scripts/phase5-matrix.mjs` contra datos reales: su reset es destructivo y el script exige explícitamente `127.0.0.1:5432/taller_automotriz`.
4. Configurar un `AUTH_SECRET` aleatorio distinto del local y `AUTH_URL` igual al origen HTTPS real; no publicar esos valores. Antes de habilitar usuarios reales, retirar/reemplazar las credenciales demo mediante una decisión de seguridad separada. Verificar sesiones, 401/403, rutas y transacciones de pagos concurrentes **con Prisma 6.0.0 y el pooler real**, además de migración directa. La [guía actual de Prisma para Neon v6](https://www.prisma.io/docs/orm/v6/overview/databases/neon) usa adaptadores y ejemplos de versiones v6 posteriores; no aplicar esas instrucciones ni instalar adaptadores sobre este proyecto 6.0.0 sin validar compatibilidad y aprobar el cambio. El flag `pgbouncer=true` depende de la versión del pooler; no añadirlo a ciegas.

## Límites de planes gratuitos y requisitos no cubiertos

Cifras consultadas el **2026-11-16**; cambian con las condiciones de cada proveedor. [Neon Free](https://neon.com/pricing): 100 CU-h por proyecto al mes, **1 GB** PostgreSQL por proyecto (20 GB por cuenta), **5 GB** de transferencia pública por proyecto al mes y suspensión del cómputo tras agotar CU-h/egress; scale-to-zero tras 5 minutos de inactividad. Su historial gratuito es de 6 horas y no incluye snapshots programados ni SLA de uptime. [Vercel Hobby](https://vercel.com/docs/plans/hobby): **4 CPU-h** de funciones, **360 GB-h** de memoria, **1 millón** de invocaciones y **100 GB** de Fast Data Transfer incluidos; al exceder límites suele haber que esperar al siguiente periodo. Revisar precios, uso permitido y cuotas vigentes antes de cualquier decisión.

Estos niveles **no garantizan** RNF-04 (disponibilidad 99,5 %), RNF-05 (respaldo diario) ni RNF-07 (50 usuarios simultáneos). El pooler admite conexiones cliente, no equivale a capacidad de 50 usuarios con latencia aceptable. Se necesitarían respaldo/restauración verificables, medición de carga y un acuerdo de disponibilidad antes de reclamar esas metas.

## Riesgo conocido: `jose` en Edge Runtime

`npm run build` puede emitir advertencias desde `jose/dist/webapi/lib/deflate.js` sobre `CompressionStream` y `DecompressionStream` no soportados en Edge Runtime, con traza hasta `next-auth`/middleware. El build local puede terminar con código 0, pero **eso no prueba compatibilidad del middleware en Edge**. No suprimir advertencias ni cambiar Next/Auth.js/`jose` sin aprobación.

Cómo verificar en un entorno autorizado: conservar la salida completa de `npm run build`, comprobar si persiste la advertencia y ejecutar login de ambos roles, logout, redirección sin sesión, 403 de páginas y 401/403 de API en el runtime objetivo. Observar logs del middleware y errores de importación/compresión con una sesión real; si falla, detener el despliegue y decidir una corrección de compatibilidad por separado. Esta verificación **no se ejecutó en Vercel**.
